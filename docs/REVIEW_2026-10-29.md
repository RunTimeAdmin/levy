# LEVY Security Review — Current Main

**Review date:** 2026-10-29  
**Repository/revision:** `RunTimeAdmin/LEVY`, `main`, `f8005b33eb0b7fa9d0910ec4547be1d25538778f`  
**Remote comparison:** `origin/main` matched the reviewed SHA.  
**Checkout:** clean after review; no tracked project files changed.  
**Decision:** **NO-GO for mainnet**

## Executive summary

No Critical or High vulnerability was confirmed in this pass. The core protocol remains non-custodial: subscribers approve USDC and the manager transfers collected funds directly to the merchant and fee router in the same transaction. The deployed-contract design is constructor-based rather than proxy-upgradeable, and I found no new direct token-theft path in the reviewed current-main contracts.

That is not a mainnet clearance. Four material Medium risks remain in the keeper/API system: the API receives the keeper’s hot key and webhook signing-key material; permissionless plan/subscription creation can impose unbounded keeper-paid work; loss of the keeper database does not rebuild dunning state or full invoice history; and a database can be silently reused against a different chain/manager. There are also lower-severity replay, configuration, wallet-flow, deployment reproducibility and analytics-measurement gaps. The repository itself states that it is not audited or deployed to mainnet. The current testnet soak is incomplete in the recorded log, and mainnet Safe readiness and the live host were not independently verified.

No chain reads, deployment, signing, transactions, pushes, PRs, or cloud agents were used. ## Findings

### Medium — F-01 — API container receives keeper and webhook signing secrets

- **File/lines:** `ops/docker-compose.yml:24-32,46-58`; `keeper/src/config.ts:56-70`; `api/src/server.ts:35-57,386-394`; `keeper/src/webhooks.ts:63-88`.
- **Impact:** The API service gets the same complete environment file as the keeper and mounts the same data volume. Thus API code/process compromise can expose `LEVY_KEEPER_KEY` and read the private webhook signing key. The keeper key pays gas rather than holding subscriber principal, so this is not an identified direct path to steal user balances. A stolen webhook key can, however, forge events accepted by merchants and the gas key can be abused for transactions that consume its balance. The public-key route also loads the signing key from the shared location.
- **Exploit sketch:** An attacker obtains code execution in the internet-facing API container through an application/dependency flaw or host exposure, reads the environment and shared volume, then extracts the keeper key and signs forged webhook payloads. This is conditional on API compromise; no such exploit was found in the reviewed source.
- **Fix brief for Claude:** Split secret and storage boundaries. Only the keeper should receive the keeper key and private webhook signer, and only it should mount a private signing-key volume. Give the API the webhook public key/key ID only. If SQLite must remain shared, keep that data mount separate from the key mount. Make signing-key creation atomic and keeper-only; add a regression test proving the API cannot read or create the private key.
- **Evidence/status:** Confirmed from Compose mounts and environment wiring. The API has a route that loads the signing key to serve its public representation. No private values are included here.

### Medium — F-02 — Permissionless plan creation creates unbounded keeper-paid work

- **File/lines:** `src/SubscriptionManager.sol:143-164,173-239,241-279,331-343`; `keeper/src/keeper.ts:49-82`; `keeper/src/db.ts:269-282,326-330`.
- **Impact:** Any wallet can create plans and subscriptions. The keeper queries all due subscriptions/retries, processes them sequentially, and has no per-cycle work cap, per-merchant quota, gas budget, or cheap-plan policy. A third party can create many low-cost self-funded plans/subscriptions or free-trial subscriptions and cause the keeper to spend its gas balance on recurring charges/failures. For a plan with large `maxFailed`, a failed subscription can consume many transactions before the contract auto-pauses it. This is an availability and operating-balance risk, not theft of subscriber funds.
- **Exploit sketch:** An attacker creates a plan with a one-day cycle and free trial, subscribes many addresses/instances with no allowance, and waits for trial expiry. The keeper attempts every due item; repeated failed pulls become on-chain failure transactions until auto-pause. Self-funded minimal-price plans can instead remain chargeable and recur.
- **Fix brief for Claude:** Add keeper-side bounded scheduling: per-cycle transaction and gas budgets, a maximum batch, fair per-merchant quotas, queue-age monitoring, and a safe pause/skip policy for uneconomic workloads. Consider on-chain limits or a merchant admission/deposit policy only if it fits the permissionless product model. Add adversarial integration tests that create many plans/trials and prove budget and fairness behavior.
- **Evidence/status:** Reachable from public contract entry points and unbounded keeper/database iteration. Exact mainnet transaction fee economics and attack cost were not independently measured.

### Medium — F-03 — Database loss does not restore dunning or complete history

- **File/lines:** `keeper/src/indexer.ts:78-99,281-291`; `keeper/src/db.ts:269-282,326-330`; `src/SubscriptionManager.sol:331-343`.
- **Impact:** Dunning rows exist only in SQLite. On startup, `backfillAll()` repopulates current plans and subscriptions, but not the dunning queue. Past-due subscriptions are excluded from the normal due sweep and are retried only if a local dunning row exists. After losing the database, the keeper therefore stops its scheduled retries for those subscriptions until an external caller charges them or a subscriber takes recovery action. A fresh database also starts log sync at the configured lookback (default 5,000 blocks), not necessarily at deployment, so old invoices/failures/webhook events are not fully reconstructed.
- **Exploit sketch:** A disk failure or operator restores an empty database. The keeper reads a subscription’s `PAST_DUE` state from chain, but creates no retry row; its normal due query excludes that state. The merchant/customer sees no automated retry, and the API history may be incomplete.
- **Fix brief for Claude:** Add explicit recovery mode. Rebuild due-retry state using on-chain `failedAttempts` and `lastFailedAt`/`retryGap`, reconcile paused/cancelled states, and make the historical scan start from a durable deployment block/checkpoint when rebuilding. Add a database-loss integration test that proves retries, invoice rows and webhook recovery match chain state. Document backup/restore and test it on a disposable environment.
- **Evidence/status:** Source path is confirmed. Whether third parties routinely call `charge()` is outside the product’s recovery guarantee; no recovery drill was run.

### Medium — F-04 — SQLite state is not bound to chain/manager identity

- **File/lines:** `keeper/src/config.ts:56-72`; `keeper/src/indexer.ts:17,78-99`; `keeper/src/db.ts:243-260,446-455`; `api/src/server.ts:162-177`; `api/public/checkout.js:62-84,148-180`.
- **Impact:** The same database path can be used after changing `LEVY_CHAIN_ID`, manager or USDC. The cursor key is global, plans are inserted with `ON CONFLICT DO NOTHING`, and startup does not verify stored chain/manager/token metadata. The API returns the local plan catalogue; checkout displays those cached prices and submits a plan ID to the configured manager. A stale DB can therefore show the wrong plan/price, retain stale subscriptions, or make the keeper repeatedly attempt IDs that do not exist on the newly configured manager. A user may approve based on stale terms while the on-chain plan at that ID differs.
- **Exploit sketch:** An operator points a new-chain/new-manager deployment at an old SQLite volume. `backfillAll()` does not clear or overwrite existing plan rows; the public plan endpoint and checkout can continue serving the old values while the wallet targets the new manager.
- **Fix brief for Claude:** Persist `(chainId, managerAddress, usdcAddress, deploymentBlock)` as immutable database identity and fail closed at keeper and API startup on mismatch. Namespace per deployment or require an explicit migration/reset. Reconcile stale rows when a legitimate deployment migration is supported; add a test that deliberately reuses a DB with different addresses and expects refusal.
- **Evidence/status:** Confirmed from config, cursor, upsert behavior and public plan route.

### Low — F-05 — Replayed chain logs can enqueue duplicate signed webhooks

- **File/lines:** `keeper/src/indexer.ts:88-99,187-213`; `keeper/src/db.ts:287-305,512-520`; `keeper/src/webhooks.ts:114-136`.
- **Impact:** The cursor advances after an entire log chunk. A crash after processing a log but before committing the chunk cursor can replay already handled logs. `insertCharge()` deduplicates charge rows, but its result is ignored before webhook event generation; failure rows and webhook deliveries lack a stable key derived from the source chain event. A replay gets a fresh delivery ID, so receiver-side deduplication by delivery ID cannot identify it as the same underlying charge/failure. A merchant that performs non-idempotent fulfillment may act twice.
- **Exploit sketch:** The keeper processes a `Charged` event and queues a webhook, then crashes before updating the chunk cursor. On restart it reprocesses that event and queues another signed delivery with a different ID.
- **Fix brief for Claude:** Add a unique source-event key containing chain, manager, transaction hash and log index; make event handling and delivery enqueue idempotent in a transaction. Emit only when the source event is first inserted. Derive a stable per-webhook delivery key from that event, while keeping separate retry attempts. Add crash/replay tests at the boundary between event handling and cursor advancement.
- **Evidence/status:** Confirmed from control flow and schema. The repository’s current test suite does not simulate a crash between handling and cursor commit.

### Low — F-06 — Dunning configuration accepts intervals shorter than contract rules

- **File/lines:** `keeper/src/config.ts:47-53`; contract `src/SubscriptionManager.sol:320-329,331-343`; `keeper/src/dunning.ts:11-18`.
- **Impact:** `dunningDays()` checks only that values are positive finite numbers. It accepts fractional or too-short intervals, although the contract enforces 1 day, then 3 days, then 7 days between failed pulls. A configured retry can be rejected during gas estimation with `RetryTooSoon`; the keeper’s in-memory backoff may then retry later, but it resets on restart. This delays recovery and creates repeated failed estimates rather than honoring the configured schedule.
- **Exploit sketch:** An operator configures `LEVY_DUNNING_DAYS=0.5,1,2`. At least one retry is scheduled before the contract’s minimum and cannot be broadcast successfully.
- **Fix brief for Claude:** Validate the configured schedule against the contract’s `retryGap` minima (and use whole seconds/days unless fractional scheduling is intentionally supported). Fail startup with the exact mismatching index and add tests for fractional and too-short intervals.
- **Evidence/status:** Confirmed configuration accepts these values; an actual production deployment using them was not observed.

### Low — F-07 — Treasury handover can drop the contract-treasury policy

- **File/lines:** `src/FeeRouter.sol:43-60`; `script/Deploy.s.sol:67-73`; `ops/treasury-multisig.md:75-78`.
- **Impact:** Deployment on Arc mainnet requires the initial treasury to have code, but `proposeTreasury()` accepts any non-zero address and `acceptTreasury()` does not require the successor to be a contract or Safe. The current treasury can therefore intentionally or mistakenly move future fee revenue to an EOA. This is a governance-policy mismatch, not an unauthenticated exploit: the current treasury must authorize the proposal and the new address must accept.
- **Exploit sketch:** A compromised or misoperated treasury Safe proposes an attacker-controlled EOA; that address accepts; later permissionless sweeps send fees to the EOA.
- **Fix brief for Claude:** Decide whether EOA successors are allowed. If the mainnet invariant is “treasury must remain a threshold Safe,” enforce a validated successor policy or a timelocked governance path and verify it in deployment/operations checks. If governance intentionally retains this power, document it as a trusted-authority assumption and monitor `TreasuryProposed`/`TreasuryUpdated`.
- **Evidence/status:** The transition is confirmed in code and documented as an operational risk. The live mainnet Safe is not deployed/verified in this review.

### Low — F-08 — Browser flows can repeat or overstate an approval after unknown outcomes

- **File/lines:** `api/public/checkout.js:20-38,113-124,148-180`; `api/public/portal.js:232-263,267-283`; `api/public/wallet.js:97-119`.
- **Impact:** Checkout persists pending transactions in local storage for one day, but tabs do not coordinate; a second tab can proceed even if it finds an in-flight subscription record. If an unknown result is forgotten/expired/storage is unavailable, a repeat can create another valid subscription. Separately, the portal top-up path does not persist the approval hash/target. If an approval mines but its receipt is not observed, the button is re-enabled; repeating after the allowance updated computes another increment and can leave more allowance than the user intended. Wallet prompts still require user action; this is a transaction-consent and UX safety gap, not an automatic drain.
- **Exploit sketch:** The user starts a checkout in one tab and retries from another before the first result is reconciled, or repeats “Top up” after an approval succeeded but the receipt timed out. The second flow can create another subscription or add another allowance increment.
- **Fix brief for Claude:** Use durable pending-operation records keyed by chain, contract, wallet and action; coordinate tabs with a browser lock/BroadcastChannel; persist transaction hash and target allowance; reconcile receipt and on-chain state before enabling retry. Preserve the ability to intentionally create multiple subscriptions, but require the UI to resolve an outstanding transaction first.
- **Evidence/status:** The write paths and `unknown` receipt behavior are confirmed. No unauthorized wallet signature occurs without user approval.

### Low — F-09 — Wallet chain is checked at connect, not immediately before each broadcast

- **File/lines:** `api/public/wallet.js:70-90,97-119`; `api/public/checkout.js:113-159`.
- **Impact:** If the user changes networks after `connect()` and before a later transaction, `send()` does not compare the current chain to the server-configured chain. Depending on the target address and wallet state, a transaction may be sent on the wrong network or simply fail and waste gas. No wrong-network fund loss was reproduced.
- **Exploit sketch:** A page loads Arc config and connects successfully; the wallet is switched in another tab or wallet UI; checkout then sends approval/subscribe without a fresh `eth_chainId` check.
- **Fix brief for Claude:** Recheck `eth_chainId` immediately before every transaction and read operation that affects a transaction; listen for `chainChanged` and invalidate stale page state. Add tests that switch chain between connect and send.
- **Evidence/status:** Confirmed in helper code; impact beyond failed/wasted transactions is unverified because no destination-chain contract deployment was assessed.

### Low — F-10 — Permissionless plan spam can make API catalog and startup work grow without a bound

- **File/lines:** `src/SubscriptionManager.sol:143-165`; `keeper/src/indexer.ts:166-169,281-291`; `api/src/server.ts:170-177`; `api/public/checkout.js:62-68`.
- **Impact:** Anyone can create plans. The keeper iterates every plan on full backfill, and the public `/api/plans` route returns the entire local catalogue; checkout fetches the whole list to find one plan. Plan creation costs the attacker transactions, so this is not free, but repeated creation can increase startup time, database size and response/rendering costs for public pages.
- **Exploit sketch:** A wallet creates many plans over time; a keeper restart performs an O(planCount) backfill, and each public checkout downloads all plans even though it needs only one.
- **Fix brief for Claude:** Add a paginated/filterable plan API and `GET /api/plans/:id` for checkout. Bound page size and client rendering. Measure keeper backfill at high plan counts; if needed, use incremental/indexed recovery rather than loading every plan synchronously. Consider per-merchant limits only if compatible with permissionless plan creation.
- **Evidence/status:** Reachable source paths are confirmed; no load test or current high-count deployment was assessed.

### Info — F-11 — New actor-count script needs input validation and an explicit metric contract

- **File/lines:** `script/count-unique-actors.py:64-90,102-143`; `script/test_count_unique_actors.py:57-85,116-149`.
- **Impact:** `--chunk` has no positive-value check. A zero/negative chunk yields inverted/non-progressing block ranges; a conforming RPC will likely reject the malformed query, but a nonconforming endpoint may return empty results and prevent progress. The script also records the RPC’s chain ID without requiring the expected chain ID. Its metric is transaction `from` addresses, not necessarily end-user contract callers (`msg.sender`/subscriber); the keeper is included in the test fixture as an actor. Therefore the number is a transaction-sender estimate, not automatically a count of unique customers or eligible users.
- **Exploit sketch:** An operator passes `--chunk 0` or connects to the wrong RPC, then treats the output as a valid network/user count. A Safe, relayer or account-abstraction transaction can make the transaction origin differ from the contract-level account.
- **Fix brief for Claude:** Reject `chunk <= 0`, validate block and address formats, add required `--expected-chain-id` (or a clearly configured expected network), and make the output name/metadata state whether it counts transaction origins, contract callers, subscribers, merchants, or unique wallets. If a program’s eligibility is based on users, count the appropriate indexed event fields and separately report keeper/service transactions. Add tests for invalid chunks, wrong chain and Safe/relayer semantics.
- **Evidence/status:** The aggregation behavior and missing checks are directly visible. The external Builder/allocations eligibility rule was not verified; do not treat this script alone as proof of eligibility.

### Info — F-12 — RPC credential in a command-line URL can leak locally

- **File/lines:** `script/count-unique-actors.py:102-114`.
- **Impact:** The script requires the RPC endpoint as `--rpc`. Providers commonly embed credentials in URL paths or query strings; a literal command can then appear in shell history and process arguments. The script does not itself print the parsed URL, but the invocation may expose it to local users/process inspection.
- **Exploit sketch:** An operator runs the script with a credential-bearing URL directly in the command line; a same-host user with process visibility or later access to shell history reads it.
- **Fix brief for Claude:** Accept the endpoint from an environment variable or protected file/stdin, document shell-history risks, redact URL-bearing errors, and avoid logging raw arguments. Keep this script read-only and use a low-privilege RPC credential.
- **Evidence/status:** Command-line parameter use is confirmed; host `/proc` visibility and actual operator invocation are unverified.

### Low — F-13 — Build/release evidence is not fully reproducible

- **File/lines:** `foundry.toml:1-8`; `foundry.lock:1-7`; `.gitmodules:1-6`; `.github/workflows/ci.yml:13-40`; `keeper/test/integration.test.ts:21-23,126-138`.
- **Impact:** Foundry does not pin the Solidity compiler. `foundry.lock` records OpenZeppelin revision `cab19933…`, while the repository Git submodule link is `4858ab13…`; the submodule was not initialized here, so whether this is only stale metadata or a different dependency tree is **unverified**. CI checks ABI JSON drift, but the keeper’s Anvil test deploys `.bin` artifacts and the check does not compare those bytecode files. A green test run therefore does not prove the shipped/deployed artifact is reproducible or that all ABI/bytecode pairs match.
- **Exploit sketch:** A release is rebuilt with a different compiler/dependency snapshot or stale keeper bytecode; tests still use mismatched ABI/bytecode inputs or deployment source verification cannot reproduce the exact artifact.
- **Fix brief for Claude:** Pin the exact Solidity compiler and reconcile lockfile/submodule commits. Generate ABI and bytecode artifacts from the same build and compare both in CI. Preserve build inputs and compiler metadata alongside deployments, and verify exact deployed source/bytecode before mainnet.
- **Evidence/status:** Compiler pin absent and revision records differ. The practical bytecode/code-body impact was not locally reproduced because Foundry and submodules were unavailable.

### Low — F-14 — Ignore rules do not cover common local secrets/state files

- **File/lines:** `.gitignore:1-6`; `ops/.env.example:16-41`.
- **Impact:** Only `ops/.env` is explicitly ignored. A root `.env` (a natural place for Foundry’s `DEPLOYER_PRIVATE_KEY`), PEM signing-key files and SQLite sidecars are not covered by these rules. This increases accidental-commit risk. No such value was found in tracked files by the heuristic scan.
- **Exploit sketch:** A developer creates a root `.env` or local signing-key file and stages all files; the current ignore file does not prevent the credential/state file from being committed.
- **Fix brief for Claude:** Add narrowly appropriate ignore rules for root dotenv files, private-key/PEM files and SQLite database/WAL/SHM files, with explicit force-add instructions only for safe examples. Add a CI secret scan that reports file paths/lines without echoing values, and a pre-commit check for local credentials.
- **Evidence/status:** Ignore rules are confirmed; no leaked credential was identified in the tracked-file scan.

## Design risks and operational gaps

1. **Testnet soak is not complete in the checked-in evidence.** `ops/testnet-soak.md:230-253` shows the pass criteria unchecked and the log ending with day-zero/day-one entries dated 2026-10-26/27. The planned week-long soak had not completed in this recorded evidence as of the review. Run the whole soak on the exact release candidate, including restart/database-recovery, duplicate-event, Permit2, dunning, pause/cancel, treasury handover and webhook replay cases.
2. **No mainnet deployment or paid audit is evidenced.** README states “Not on mainnet. Not audited.” The mainnet Safe is a proposed structure; `ops/treasury-multisig.md:20-35` lists unresolved signer/threshold checks. The actual Safe address, threshold, owners/modules, treasury wiring, deployment bytecode and key custody remain unverified.
3. **Live infrastructure was not checked.** A prior infrastructure document describes a shared VPS and hardening, but this review did not connect to the host. Dedicated keeper isolation, current network exposure, actual env/file permissions, API rate limits, backups, alerts and restoration remain unverified. Do not infer they are correct from runbooks.
4. **Merchant integration must not treat `ref` as proof of identity.** A subscriber chooses the public `bytes32 ref`; it is useful as an opaque correlation value, not authentication. Merchants should verify the subscriber, plan and on-chain status and bind their own records to `subId`. A future signed checkout intent could bind merchant, plan, wallet, reference, nonce and expiry.
5. **Permit2 allowance warnings are incomplete.** The keeper’s runway logic checks the direct ERC-20 allowance, not the Permit2 allowance (documented in `ops/testnet-soak.md:128` and keeper comments). Permit2 users may be reported as low even when their Permit2 allowance is valid. Confirm expiration and pull authority before warning or billing UX relies on the result.
6. **Treasury controls protect project fees, not subscriber funds.** The FeeRouter can accumulate protocol fees until swept. A safe migration policy is important, but the current router has no user-principal custody or treasury upgrade key over the manager.
7. **`main` does not include Manager v2.** The README lists payout-address separation, plan retirement/limits, intro pricing and wallet migration on a separate branch. Those features introduce new authorization, billing and migration states and need a separate code review and audit before deployment.

## Mainnet decision

**NO-GO for mainnet.** The main blockers are the shared hot-key/signing-key boundary, unbounded keeper-paid work, missing dunning/history recovery and missing chain/manager binding on persisted state. These should be fixed and regression-tested before exposing real users or funding a production keeper. The wallet transaction recovery and event idempotency gaps also need resolution or explicit risk acceptance.

Separately, complete the week-long testnet soak on the release candidate; verify the Safe’s actual threshold/owners and treasury; establish isolated key custody, database backup/restore and monitoring; pin/reconcile build inputs; and obtain an independent paid audit. Reassess Manager v2 separately. No high-severity on-chain theft issue was confirmed, but the available evidence is insufficient to recommend mainnet launch.

## Feature opportunities (prioritized)

1. **Keeper safety and recovery (launch-gating):** bounded queue processing, per-merchant fairness, a gas-spend budget, and automatic recovery of dunning/history from on-chain state. This reduces service-depletion risk without taking custody of subscriber funds.
2. **Event-driven idempotent integrations:** stable event IDs based on chain transaction/log identity; replay-safe webhook delivery, per-merchant fairness and explicit retry visibility. This prevents duplicate fulfillment and makes integrations safer.
3. **Allowance intelligence:** combine direct USDC and Permit2 allowance/expiry reads in the portal and merchant alerts, showing what is actually spendable and for how many cycles.
4. **Verified merchant checkout:** merchant profile/domain verification and signed checkout intents bound to a wallet, plan, reference, expiry and nonce. Keep the current transparent merchant address and avoid treating an opaque reference as identity proof.
5. **Smart-account support:** EIP-1271/Safe SIWE authentication and clear Safe/account-abstraction transaction UX. Test that the displayed account matches the on-chain `msg.sender` semantics.
6. **Plan/API scalability:** a direct plan-by-ID endpoint, pagination, filters and bounded rendering; show all terms from authoritative on-chain reads immediately before signing.
7. **Reliable transaction recovery:** cross-tab pending-transaction coordination and persisted allowance targets for checkout/top-ups, while still permitting deliberate multiple subscriptions.
8. **Product roadmap (after separate review):** Manager v2’s payout address, plan retirement, finite billing periods, introductory pricing and wallet migration. These are valuable merchant features but increase state-machine and authorization complexity; design, test and audit them independently.
9. **Auditable analytics:** publish both transaction-origin counts and event-role counts, with explicit chain ID, block range/finality policy, contract list and reproducible methodology. Do not label transaction senders as unique customers unless that is the intended eligibility definition.

## What an outside audit should still cover

The paid audit should cover the exact post-fix release tag and deployment artifacts, not just the current `main` source. Include the SubscriptionManager lifecycle and invariants; FeeRouter handover policy; Permit2’s real deployment and allowance/nonce behavior; Arc USDC compatibility and fee assumptions; keeper scheduling, gas exposure, database recovery, event idempotency, chain identity, and transaction/retry logic; SIWE/API tenant isolation; webhook signing, replay and SSRF controls; all browser approval/unknown-outcome flows; Docker, secret separation and deployment handover; dependency/compiler reproducibility; and the actual mainnet Safe/host/runbooks. Require adversarial crash/restart tests, exact-SHA fuzz/invariant results, bytecode verification, and an independent soak review. Static analysis and mutation testing should be included or their absence explicitly accepted.
