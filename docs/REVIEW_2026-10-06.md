# Levy repository review (third external review)

Received 7 October 2026, pasted in verbatim. The evidence in it is dated 6 October 2026 and refers to `5a4527f`. Triage against the code and the live testnet: `SECURITY_REVIEW.md` section 9.

---

**Levy has made real progress since the October 2 review, but the replacement Arc testnet deployment has still not processed a subscription.** Current `main` is [`5a4527f`](https://github.com/RunTimeAdmin/levy/commit/5a4527f6c5af184152e6932de609665ac62c48b6). Its contracts, keeper, API, dashboard, checkout and portal form a credible USDC recurring-billing system. The gap between working code and demonstrated billing remains substantial. On October 6, read-only calls to the current manager returned **zero plans and zero subscriptions**; the public API returned an empty plan list. The seven-day billing-soak checklist has no completed merchant, subscriber or pass-criterion entries. This is a release-evidence problem, not proof that `charge()` is broken. Levy should remain a testnet product, not be presented as ready to bill real customers on mainnet. [1] [2] [3]

I reviewed the private repository against the [4], tested the current detached snapshot locally, and checked the public testnet with read-only calls. I did not edit source, sign into the app, connect a wallet, submit a transaction or change the deployment. This is not an external audit or a test of the private host's actual backups and alerts.

## The October 2 fixes are meaningful

The most important correction is **on-chain dunning timing**. Levy now enforces a one-day gap after the first recorded failure, three days after the second, and seven days thereafter. A stranger calling the permissionless `charge()` function cannot manufacture daily failures to accelerate a customer's auto-pause. The contract and regression tests cover the hostile daily-caller case, and the deployed manager's read-only `retryGap(1/2/3)` calls returned 86,400, 259,200 and 604,800 seconds. A customer who restores funds can still be charged without waiting out a failure gap. [5] [6]

The deployment script now refuses noncanonical USDC and Permit2 addresses **on Arc mainnet**. The currently deployed testnet manager points at Arc's published USDC and Permit2 addresses. Its dependency getters and FeeRouter wiring were checked with read-only calls; the testnet-only override looseness remains a smaller configuration risk. [7] [8]

The browser wallet now checks the actual chain again after a switch or add request. USDC amounts below one cent are no longer presented as `$0.00` just because they were truncated to two decimals. Checkout also saves transaction hashes after broadcast, treats an unread receipt as **unknown**, and provides a recovery link rather than inviting the ordinary same-tab blind retry. These are genuine customer-safety improvements, but they do not yet make a recurring checkout idempotent in every browser state. [9] [10]

The public site's status is more candid than in the previous review. It now describes the week of real billing as **next work** and says an external audit and mainnet come later. The new public merchant documentation is useful and clearly marks the current chain as testnet. [11] [12]

## The remaining launch blockers

### A checkout can still create two obligations after an ambiguous outcome

A successful no-trial `subscribe()` creates a fresh subscription and bills the first cycle immediately. The new pending record lives in browser `localStorage`, expires after 24 hours and silently becomes empty if storage fails. A second tab that was already connected before the first broadcast reads pending state on its Go path but does not stop before approving or subscribing. A successful transaction with an unread receipt can therefore be followed by a second transaction from a pre-connected tab, or after the record is lost or expires. This is a **source-traced risk**, not an observed customer incident. Multiple subscriptions can be legitimate, so simply banning duplicates by wallet and plan would be the wrong fix. [13] [14]

There is a related hole in the **subscriber portal**. Its Top up button reads the current shared allowance and adds the requested rounds. It does not persist the approval hash or fixed target. If the approval was mined but its receipt could not be read, the button is re-enabled. Clicking again can add the same rounds a second time. That does not transfer USDC at the moment of approval, but it grants a larger spending allowance than the customer selected. [15] [10]

Before real-money billing, persist an unresolved order and its transaction identity beyond a one-day browser timer. Coordinate tabs and reconcile the chain result before another subscribe is offered. For portal Top up, persist the **target allowance**, not an instruction to add rounds again, and treat unknown as pending. Test a successful but unreadable approval and subscription, an already-connected second tab, blocked/cleared storage, reload and a late receipt. An opaque merchant order ID can make intended repeat purchases distinguishable from accidental repeats.

### Losing the keeper database can stop retries for past-due customers

The keeper rebuilds plan and subscription rows from the chain after a fresh start. It does **not** reconstruct its dunning schedules. Ordinary due work excludes `PAST_DUE` subscriptions, while retry work requires a stored dunning row. If SQLite is lost or restored incompletely, a customer can top up and remain chargeable on-chain but never receive the expected automatic retry. Levy's own keeper README notes the database-loss caveat. No actual production database loss was observed here. [16] [17] [18]

Make the chain the recovery source for missing schedules: inspect each past-due subscription's on-chain failure count and last failure time, derive its next permitted retry, and alert when a past-due subscription lacks a corresponding row. Prove this with a destructive database-restore integration test that reconciles the eventual charge, invoice and webhook. A persistent Docker volume is helpful, but it is not the same thing as a tested backup and restore.

### The replacement contract still needs its first real end-to-end week

The live manager is `0x62a6512335d630ef19fcadb497adf98d883f77c6`. It exists and its retry and dependency getters answer as expected. Yet `planCount() = 0`, `subCount() = 0`, and `/api/plans` returned `[]` during this review. The soak log records the October 3 redeployment and setup, not an actual charge, webhook, keeper restart or merchant reconciliation on this instance. [2] [3]

Run the repository's own day-zero through day-seven matrix on **these exact addresses**. Record testnet transaction hashes, subscription IDs, all ten webhook event types, keeper charge latency, failure and recovery, pause/cancel/plan changes, Permit2, fee sweep, and agreement between chain amounts, API records and exported CSV. That evidence should be reviewed before an external audit or mainnet plan. The current public site is right not to claim the week has already happened.

## Risks worth fixing during that soak

**Indexer replay can duplicate business events without charging twice.** The sync cursor advances only after a chunk's events are handled. A crash before that write replays events. Charges have a database uniqueness key, but the return value of `insertCharge()` is ignored and webhooks are still enqueued. `ChargeFailed` rows have no event-identity uniqueness key at all. Webhook enqueues allocate fresh delivery IDs, so a merchant deduplicating only `X-Levy-Delivery` can see two distinct deliveries for one on-chain event. Catch-up also timestamps old failures with the *current head* time rather than their block time, which can postpone retries. These effects are inferred from the current source, not reproduced in a running keeper. [19] [20] [21]

Use chain transaction hash plus log index as the unique event identity. Commit event effects, webhook queueing and cursor progress consistently. Derive failure time from the event block or an on-chain `lastFailedAt`, not the catch-up time. Add a test that crashes after event handling but before cursor commit, then restarts. The test must show one failure row and one logical webhook event. It must also show a retry time based on the original failed transaction.

**Unlimited uneconomic work remains possible.** Anybody can create a one-unit, one-day self-subscription. Its 1% fee rounds down to zero, but Levy's keeper would pay to charge it every day and currently sweeps all due rows. Enough of these could exhaust keeper USDC or delay genuine customers. This is an availability and economics issue, not a way to redirect subscriber funds. Choose a clearly disclosed operator service policy, such as allowlisted merchants during launch, economic admission, quotas or merchant-funded execution. Then load-test a mixture of legitimate and deliberately uneconomic plans and alert on backlog and gas burn. [22] [23]

**Customers still see an address instead of a merchant.** Hosted checkout shows the price, cadence, raw merchant address and plan number, but no domain-verified business name, product/service description or cancellation/refund policy. The authorization should bind versioned merchant and plan terms to the on-chain payout address, show domain-control evidence, and preserve the accepted terms on a receipt. This is about informed consent and phishing resistance, not a defect in the contract's payment destination. [24]

Two smaller mismatches should be cleaned up. The wallet checks network at connect time, not immediately before each later read or send, so a user changing networks mid-session can bypass the stale connection check. And webhook documentation says failures are retried for 24 hours, but the current backoff rule makes its last scheduled attempt at about **19 hours 21 minutes**, then dead-letters instead of making an attempt near the 24-hour boundary. Test the full timeline or correct the promise. Permit2 is still mock-tested in the repository; the documented testnet Permit2 path has not been exercised on the current manager, and direct-manager allowance warnings do not yet reflect a Permit2 allowance. [10] [25] [26] [27]

## What I validated and the practical next step

The clean current snapshot built under Foundry's CI profile. **57 ordinary contract tests and the invariant suite passed**, including the new failure-cadence cases. The API passed TypeScript and **55/55** tests. The keeper passed TypeScript and **55/55** tests, including its Anvil integration cases; I also ran its **10/10** integration tests separately. Production-only `npm audit` reported zero advisories for both Node lockfiles at review time. These results show good local test health, not proof of live billing or a formal security audit. No Docker executable was available locally, so I did not rerun the image builds. [28]

I also compared the two live testnet runtime bytecodes to artifacts compiled from current source. **The executable bytecode matched after masking constructor immutables**, but each artifact differed in 33 bytes within the Solidity metadata tail. The current README says the original deployment build matched; my independent comparison does not establish an exact metadata-level match to that historical build. The explorer still does not show independently verified source. Preserve the deployment compiler inputs, verify and publish contract source, and record the actual immutable getters rather than presenting this as a full exact-byte attestation. [29]

The repository defines CI with contract, keeper, API and Docker jobs. Earlier commits show successful runs, but GitHub's Actions runs endpoint returned **zero runs for the current merge commit `5a4527f`** at review time. That does not mean current code failed CI; it means I could not establish a passing CI run for *this SHA*. Require it before promotion and investigate why the October 5 merge did not yield a visible run. The local tests above were run on the exact detached snapshot. [30]

**My order of work:** first make checkout and portal recovery fail closed, then add DB restore and indexer-replay tests. Establish keeper admission limits before opening to arbitrary merchants. Next complete and publish the fresh deployment's seven-day testnet soak. Only after those results, exact deployment provenance, and an independent contract/off-chain review should Levy be considered for mainnet. The planned token can wait; recurring-payment correctness is the product customers have to trust.
