# LEVY Security Review — 2026-10-27

**Target:** `RunTimeAdmin/LEVY`, `main` at `941d5ed73e5e5f6fc2c18df087682400f2aacf7c` (confirmed equal to `origin/main` during review). The review checkout was clean. The repository contains 156 tracked files.

**Review mode:** Read-only. No repository files, chain state, credentials, deployments, signatures, transactions, PRs, or GitHub state were changed. A path-and-line-only scan found no committed private-key value or PEM private key in the tracked tree; matches were public hashes/topics, test fixtures, placeholders, or deployment output. This was a heuristic scan, not a guarantee about untracked files or all Git history.

**Validation:** GitHub Actions completed successfully on the exact reviewed SHA: Keeper tests, API tests, Contracts (`forge`), and Docker images. I could not rerun locally because Foundry/Slither and project dependencies are absent in this review environment. Slither and mutation testing are not jobs in the current CI matrix, so those results remain unverified for this exact SHA.

## Decision: NO-GO for mainnet

No Critical or High direct contract exploit was confirmed in this pass. I found no demonstrated path that lets an arbitrary caller steal subscriber funds. The current contract design is substantially non-custodial: subscriptions pull only previously authorized USDC, charges pay the plan merchant and fee router directly, the manager is not upgradeable, and the tested manager balance is zero after settlement. The contract also uses a reentrancy guard around token-moving operations and limits failure-recording cadence.

That is not enough to approve mainnet. The keeper can be induced to spend unbounded sponsored gas and has a recovery gap for past-due subscriptions after loss of its database. The API shares the keeper key material and webhook signing key. Mainnet treasury safety is not enforced after deployment. A new actor-count utility in the current commit is materially incorrect for its stated purpose. The exact mainnet configuration, Safe owners/threshold, Arc token/Permit2 behavior, and completed soak are not independently verified here. Resolve the Medium findings below, complete the mainnet launch checklist and soak, and obtain an outside audit of the exact release and deployment configuration first.

## Findings

### Medium — M-1 — The public API has access to both the keeper key environment and webhook signing key

**Files:** `ops/docker-compose.yml:24-32,46-58`; `keeper/src/config.ts:56-70`; `keeper/src/webhooks.ts:57-83`; `api/src/server.ts:386-394`.

Both services receive the same `.env` file. The API therefore receives `LEVY_KEEPER_KEY` even though it does not need to sign keeper transactions. Both containers mount the writable `/data` volume and use the webhook private-key path. The API’s public-key endpoint calls `loadSigningKey`, which reads or can create the private signing key. That key signs messages accepted by merchant webhook receivers.

**Impact and exploit sketch:** If the internet-facing API process or container is compromised, the attacker can access the keeper’s gas-paying private key and spend its balance. The attacker can also sign forged webhook events that appear to come from Levy, potentially causing merchants to fulfill goods or update financial records based on false `charge.succeeded` notices. Neither key is exposed by a normal API response, but placing them in the API’s environment and writable filesystem expands the impact of any API compromise.

**Fix brief for Claude:** Split API and keeper secrets. Give `LEVY_KEEPER_KEY` only to the keeper. Keep the webhook private key and its writable directory keeper-only. Have the API serve a separately generated public-key file or public-key record, mounted read-only; do not call a function that can load or create the private key in the API. Rotate the webhook key after separation and document how merchants pin/update the public key. Add a deployment test that inspects the API container’s environment and mounts for absence of both private keys.

### Medium — M-2 — Permissionless free trials can create unbounded keeper-funded failure work

**Files:** `src/SubscriptionManager.sol:49-56,143-165,173-239,331-343`; `keeper/src/keeper.ts:49-82`; `keeper/src/db.ts:269-282,326-330`.

Anyone may create plans. A plan can have a trial, a one-day cycle, and `maxFailed` as high as 255. A trial subscription requires no initial USDC pull. When its first charge fails, the contract records failure on-chain and the keeper retries according to its dunning queue; the contract permits up to `2 * maxFailed` recorded failures before auto-pausing. The keeper processes every due subscription returned by unbounded queries and has no per-cycle transaction budget or merchant quota.

**Impact and exploit sketch:** A hostile operator can create a free-trial plan and self-subscribe, then repeat this across many subscriptions. The keeper pays the transaction cost to record failures and make scheduled retries. The attacker must pay the chain costs to create plans/subscriptions; the actual Arc economics and the practical scale of a gas drain were not measured, so the precise cost-to-impact ratio is **unverified**. Structurally, however, the keeper’s sponsored work has no global or per-merchant bound, and a sufficiently large workload can consume its gas balance, delay legitimate charges, and increase database/API work.

**Fix brief for Claude:** Add a configurable keeper sponsorship policy that does not require Levy to custody subscription principal: cap transactions and gas spend per cycle, rate-limit work by merchant, monitor and alert on plan/subscription growth, and skip or defer work when the sponsor budget is exhausted. Consider a conservative supported maximum for `maxFailed`. Check allowance/balance and Permit2 allowance before submitting predictable payment-failure transactions, while preserving retry behavior for recoverable cases. Add tests with thousands of due rows and a free-trial spam scenario; document that the keeper is not an unlimited gas subsidy.

### Medium — M-3 — Database recovery does not reconstruct dunning for past-due subscriptions

**Files:** `src/SubscriptionManager.sol:88-90`; `keeper/src/index.ts:21-24`; `keeper/src/indexer.ts:68-85,204-210,281-291`; `keeper/src/db.ts:139-144,269-282,326-330`.

On startup, `backfillAll()` hydrates current plan and subscription state from chain. It does not read the contract’s `lastFailedAt` mapping or create missing dunning rows. A new/empty database also starts event scanning only at `latest - initialLookbackBlocks` (default 5,000 blocks), so older `ChargeFailed` events may not be replayed. The regular due-subscription query excludes `PAST_DUE`; those subscriptions are retried only from the SQLite `dunning` table.

**Impact and exploit sketch:** After database loss, a restore from an incomplete backup, or a state reset, a subscription that is still `PAST_DUE` on-chain can be hydrated without a dunning row. It is then excluded from both the normal due sweep and the retry queue and can remain unpaid indefinitely without an operator noticing. This is a liveness and revenue failure, not a route to take subscriber funds.

**Fix brief for Claude:** Make recovery rebuild dunning from on-chain state. For each chargeable subscription, read `failedAttempts` and `lastFailedAt`, derive the next eligible retry according to the configured policy and contract’s `retryGap`, and upsert the queue. Add a destructive-database recovery test with a past-due subscription whose failure event predates the lookback window. Expose a reconciliation metric/alert for any on-chain `PAST_DUE` subscription with no dunning row.

### Medium — M-4 — The SQLite cache is not bound to the configured chain and manager

**Files:** `keeper/src/config.ts:56-71`; `keeper/src/indexer.ts:17,78-85,281-291`; `keeper/src/db.ts:243-260,446-455`; `api/src/server.ts` plan/config routes.

The event cursor is stored under a single global key, `manager_events_from_block`, with no chain ID or manager address. Startup backfills subscriptions from the configured manager, but `upsertPlan()` uses `ON CONFLICT (planId) DO NOTHING`. Old plan rows are neither refreshed nor deleted when the manager changes. Cached rows above a new manager’s `planCount` can also remain. There is no boot-time guard that the database was created for the current chain/manager/token tuple.

**Impact and exploit sketch:** If an operator points the API/keeper at a new manager while reusing the existing database, `/api/plans` can present stale names/prices/IDs from the old contract. A user may see one price in checkout while the new manager charges the price encoded in its on-chain plan. The transaction calls `subscribe(planId, ref)` and does not include the displayed price, so the wallet prompt itself may not make this mismatch obvious. Some stale plan IDs will simply revert; a reused plan ID with a different price can create a misleading-consent/overcharge risk.

**Fix brief for Claude:** Persist a database identity tuple `(chainId, managerAddress, usdcAddress)` and refuse startup on mismatch unless an explicit migration is requested. For a new identity, rebuild or migrate all chain-derived tables and remove stale plans/subscriptions. Have checkout verify the plan’s merchant, price, cycle, token, manager, and chain directly against the configured contract immediately before signing. Add a regression test that switches manager addresses while reusing a database.

### Medium — M-5 — Mainnet treasury controls are weaker after deployment than at deployment

**Files:** `script/Deploy.s.sol:63-73`; `src/FeeRouter.sol:29-33,43-60`; `test/Deploy.t.sol:61-69`; `ops/treasury-multisig.md`.

The mainnet deploy script requires the initial treasury address to contain code, but it does not validate Safe owners or threshold. More importantly, `FeeRouter.proposeTreasury()` and `acceptTreasury()` only require a nonzero proposal and acceptance by that address. They do not require the successor to be a Safe or even a contract. The deployment test treats any contract as a Safe stand-in.

**Impact and exploit sketch:** A mistaken or compromised current treasury can propose an EOA or weakly controlled contract, which can accept and become the destination for all accumulated protocol fees. This is not a permissionless exploit; it is a treasury-authority and launch-configuration risk. The contract’s two-step change protects against an unaccepted typo, but it does not preserve multisig custody after acceptance.

**Fix brief for Claude:** Decide whether treasury handover is intentionally allowed to move to any address. If mainnet policy requires a multisig, enforce an approved treasury policy on-chain where practical, or make the exception an explicit governance process with a timelock and independent review. Before deployment, verify the actual Safe address, owners, threshold, modules, fallback handler, and recovery procedure. Add tests for the documented allowed successor types and a mainnet preflight that fails unless the operational Safe checks pass.

### Low — L-1 — Replayed log chunks can enqueue duplicate signed webhooks

**Files:** `keeper/src/indexer.ts:88-99,187-213`; `keeper/src/db.ts:120-144,512-521`; `keeper/src/webhooks.ts:114-123,135-136`.

The indexer writes each log’s database effects and webhook deliveries before advancing the block cursor. A crash after some effects are committed but before `setSync()` commits the chunk cursor makes the next run process the same logs again. Charge rows have a uniqueness constraint, but `charge_failures` and `webhook_deliveries` do not have a chain-event idempotency key. A replay therefore creates a new delivery row and delivery ID. The deterministic `invoiceRef` on successful charges gives consumers a useful dedupe value, but the delivery ID alone does not identify the same on-chain event across replays.

**Impact and exploit sketch:** A merchant endpoint that treats each valid signed webhook as a new action may process the same charge/failure twice after a keeper crash or database restore. This should not cause a second on-chain charge, but it can duplicate fulfillment or internal accounting if consumers do not dedupe by invoice/event identity.

**Fix brief for Claude:** Give each chain-derived event a stable key such as `(chainId, managerAddress, transactionHash, logIndex, webhookId)` and enforce a unique constraint when enqueuing. Commit the event rows and cursor atomically per chunk, or make every handler idempotent. Document receiver-side deduplication by `invoiceRef` for charges and chain event identity for other event types.

### Low — L-2 — The current actor-count script filters the wrong event and wrong emitting addresses

**File:** `script/count-unique-actors.py:2-14,23-24,37-86`.

The script describes `0xd78a…d822` as a Permit2 transfer topic. That topic is actually the Uniswap V2 `Swap(address,uint256,uint256,uint256,uint256,address)` event. The Uniswap V2 pair source declares that event, and the signature registry maps the exact topic to `Swap` [1] [2]. Uniswap’s Permit2 `ISignatureTransfer` interface exposes nonce invalidation, not a transfer event; its implementation performs the token transfer through `safeTransferFrom` [3] [4].

The utility also filters logs by each supplied Levy contract address. ERC-20 `Transfer` logs for USDC are emitted by the USDC token contract, not by the Levy manager, and Permit2 transfers likewise result in token logs. It collects only one indexed address for ERC-20 transfers and does not reliably count both sender and recipient. As a result, the script can substantially undercount or miscount actors. Its output should not be used for Builder Allocations or similar claims without correction and independent validation.

**Impact and exploit sketch:** Running the documented command against the manager, vault, and fee treasury is unlikely to capture ordinary USDC transfers. The mislabeled topic can never serve as a Permit2 spend filter. Any reported “unique interacting addresses” may therefore be materially wrong.

**Fix brief for Claude:** Define precisely which interaction types count. Decode Levy events such as `Subscribed` and `PlanCreated` from the manager; query the USDC token contract for `Transfer` events and include both `from` and `to`; do not infer Permit2 use from an event that Permit2 does not emit. Validate the result against known transactions and a manually reconciled block range, add fixture tests for each relevant log source, and stream aggregation rather than retaining all logs in memory.

### Low — L-3 — Dunning configuration accepts intervals shorter than the contract allows

**Files:** `keeper/src/config.ts:47-53`; `src/SubscriptionManager.sol:30-39,320-329`; `keeper/src/dunning.ts:11-18`; `keeper/src/keeper.ts:154-167`.

The keeper accepts any positive finite `LEVY_DUNNING_DAYS` values. The contract enforces minimum failure gaps of 1, 3, and then 7 days. A misconfigured schedule shorter than those minimums causes the keeper to submit transactions that revert with `RetryTooSoon`; those reverted transactions spend keeper gas. The default `1,3,7` is consistent, so this requires a non-default or mistaken deployment setting.

**Fix brief for Claude:** Validate each retry interval against the corresponding on-chain `retryGap` at startup, or derive the schedule from the deployed manager. Fail closed on incompatible values and add tests for schedules that are too short. Keep longer-than-contract intervals permissible if delayed retries are intended.

### Low — L-4 — Wallet chain identity is checked before connecting, not immediately before sending

**Files:** `api/public/wallet.js:70-90,97-120`.

`connect()` checks and switches the wallet chain. The shared `send()` function then broadcasts using only `{from,to,data}` and does not re-read `eth_chainId` immediately before the request. The gap is narrow and requires the wallet/provider network to change after connection, but transaction requests do not bind a chain ID at this layer.

**Impact and exploit sketch:** If the active network changes between the earlier check and broadcast, a transaction could be submitted to a different chain where the same target address has code or a different contract state. The likely outcome is a revert, but it is a preventable wrong-chain user risk.

**Fix brief for Claude:** Pass the expected chain ID into the transaction helper and verify it immediately before requesting `eth_sendTransaction`. Repeat the check after account/network-change events, and display the network and exact merchant/amount/plan in a transaction confirmation summary. Add a test that changes the fake wallet chain between `connect()` and `send()`.

### Low — L-5 — New actor-count utility is outside automated tests and uses unbounded result accumulation

**File:** `script/count-unique-actors.py:37-57,60-95`; current CI workflow.

The new utility accumulates every matching log from the full requested history in memory and writes the final addresses only after the scan completes. It has a per-request timeout and block chunking, but no log-count bound or streaming aggregation. It is not covered by the current CI test matrix. This compounds L-2: even after fixing the event selection, broad token-history scans can consume substantial memory and fail before producing an output.

**Fix brief for Claude:** Add tests and a maximum supported scan range or server-side pagination policy. Aggregate actor addresses incrementally, persist checkpoints, and emit a completion marker only after every range succeeds. Record the chain ID, contract/token addresses, block interval, and event filters in the output so the estimate is reproducible.

## Lower-priority risks and limitations

**USDC administration and transfer behavior:** Mainnet settlement depends on the canonical Arc USDC implementation and its blacklist/freeze, pause, and upgrade controls. If the merchant or destination is blocked, `safeTransfer` can revert the full charge; no partial payment is retained, which preserves non-custodial accounting but prevents service. The mock USDC tests do not model these controls. Treat this as an external-token risk and verify the exact mainnet token and operational response before launch.

**Rounding:** The 1% fee uses integer division (`due / 100`) and rounds down. This is documented in the contract and test suite. Very small charges can therefore yield zero fee or slightly less than 1%; this is a known economic precision limit, not a demonstrated fund-loss bug. If a strict aggregate 1% take rate is required, define minimum charge sizes or a carefully tested fee-remainder design.

**Keeper configuration:** The keeper key is a hot operational key. The contract does not let it redirect subscriber payments, but compromise can burn its gas balance and disrupt service. Keep it in a dedicated secret manager, set a low balance and alert threshold, and rehearse rotation. `script/deploy-testnet.ps1` passes a testnet deploy key as a `cast --private-key` process argument; avoid copying that pattern for production keys.

**Delivery retention and operations:** Webhook retries are bounded per pass and dead-lettered, but sent/dead delivery rows are retained in SQLite. Define retention, backup, restore, disk monitoring, and queue caps before the database becomes large.

## What has improved and what remains unverified

The current contracts are not proxy-based and expose no general owner/admin role. The main payment path is reentrancy guarded. The subscriber must authorize USDC or Permit2, and charge destinations are determined from the immutable plan and fee-router configuration rather than from the permissionless caller. The regression suite includes cooldown tests and Foundry invariants for conservation, credits, terminal cancellation, and charge cadence.

The mainnet deployment checklist is not a substitute for verifying the deployed Safe and exact addresses. The current repo’s testnet-soak evidence is not a completed mainnet-like long-duration production rehearsal. I did not query a live Arc mainnet contract or independently validate the current on-chain USDC/Permit2 code in this pass. Mainnet bytecode, Safe owners/threshold, token controls, RPC log completeness/finality, and rollback/restore procedures remain **unverified**. The planned LEVY token/buyback/rewards path is also not part of the current `main` contract review and needs its own scope and audit before it is implemented or connected.

## Feature opportunities, keeping the design non-custodial

1. **Recovery and reconciliation mode:** Add a read-only operator command that compares on-chain subscriptions, last failures, plans, and event cursors with SQLite. It should rebuild dunning and fail loudly on chain/manager mismatch without moving subscriber funds.
2. **Bounded keeper sponsorship:** Add per-cycle gas budgets, per-merchant processing quotas, a queue-health dashboard, and alerts for free-trial/failure spikes. Keep subscription principal out of Levy custody.
3. **Webhook idempotency and tenant controls:** Add stable event IDs derived from chain logs, delivery retention controls, and per-merchant key rotation or a published verifier package. Preserve the current destination-binding checks.
4. **Safer checkout consent:** Re-read price and plan terms from the configured contract at signing time; show token, network, merchant, cycle, trial, and renewal amount; include a pre-broadcast chain recheck. Add smart-account sign-in only with explicit EIP-1271 verification tests.
5. **Reliable analytics:** Replace the actor-count script with an event-aware, reproducible export that records its exact filters and block range. Include known-transaction reconciliation tests before using its output in grants or allocations.
6. **Plan lifecycle improvements:** Add explicit plan deprecation/archival and migration guidance so merchants can publish a replacement plan without stale catalogs. Keep existing subscriptions and user consent intact; do not change a subscriber’s price silently.

## What a paid outside audit must still cover

The outside auditor should review the exact release commit and deployed bytecode, including `SubscriptionManager`, `FeeRouter`, Permit2 integration, fee/proration math, failure cadence, and all upgrade/deployment assumptions. They should validate the real Arc USDC and Permit2 deployments and test token blacklist/pause behavior, chain finality, RPC log ordering, and restart/reorg handling. The audit should include the keeper/API boundary, hot-key storage, database recovery and migration, SIWE/session/CSRF controls, SSRF protections, webhook signing/rotation/idempotency, and container/host hardening. It should also verify the production Safe’s owners, threshold, modules, and treasury migration path; review the completed soak and restore drill; and run independent Slither, fuzz/invariant, and mutation testing on the exact final SHA. Any future LEVY token, staking, buyback, reward, or treasury-splitting contracts must be separately included before they are connected to production.
