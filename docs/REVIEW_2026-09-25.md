# Engineering Review: Levy Subscription Billing

**Review Date:** 2026-09-25 (code as of `58ed3ba`)  
**Reviewed By:** Independent engineering review  
**Scope:** Smart contracts, keeper service, API, webhooks, tests, documentation

---

## Verdict

Levy is a well-architected pull-based USDC subscription system with solid fundamentals. The contracts are simple, focused, and correctly implement advance billing with proration. The off-chain services are thoughtfully designed—particularly the separation of charge and webhook loops, and the SSRF protections. The test coverage is thorough (135 tests, all passing) and the invariant fuzzing caught real bugs. The self-review (`SECURITY_REVIEW.md`) is honest about limitations.

However, this is early-stage code that has not yet proven itself in production. The testnet deployment is less than a day old. Several issues require attention before mainnet, but none are architectural flaws—they are implementation gaps and operational risks that can be fixed incrementally.

**Bottom line:** Sound design, competent implementation, not yet production-hardened. The code is ready for a formal audit and testnet soak, not for mainnet with real money.

## 1. Architecture and Components

### 1.1 What Levy Is

Levy is a Stripe Billing-style subscription service for Arc (a USDC-native L1). Merchants create immutable plans; subscribers approve a USDC allowance and subscribe; an off-chain keeper calls `charge()` each billing cycle; a 1% fee goes to the protocol treasury.

### 1.2 Components

| Component | Location | Purpose |
|-----------|----------|---------|
| `SubscriptionManager.sol` | `src/` | Plans, subscriptions, permissionless `charge()`, proration, on-chain dunning state |
| `FeeRouter.sol` | `src/` | Holds the 1% fee until `sweep()` sends it to treasury |
| Keeper | `keeper/` | TypeScript/viem: syncs events, charges due subs, runs dunning retries, checks allowance runway |
| Webhooks | `keeper/src/webhooks.ts` | Ed25519-signed delivery to merchant endpoints, 10 event types |
| API | `api/` | Fastify: Sign-In with Ethereum, merchant dashboard, customer portal, checkout |
| Deploy script | `script/Deploy.s.sol` | Deploys with safety checks (USDC decimals, Permit2 code, mainnet treasury is a contract) |

### 1.3 Flow: Create → Subscribe → Charge → Cancel

1. **Plan creation:** Merchant calls `createPlan(price, cycleSeconds, trialSeconds, graceSeconds, maxFailed)`. Price is immutable; repricing means a new plan.

2. **Subscribe:** Subscriber approves USDC allowance, calls `subscribe(planId, ref)`. Without a trial, the first cycle is pulled immediately (advance billing). Reverts if the pull fails.

3. **Charge:** Anyone can call `charge(subId)` when `block.timestamp >= nextChargeAt`. The contract:
   - Spends any proration credit first
   - Pulls the remainder via `transferFrom` (direct allowance → Permit2 fallback)
   - Splits 99% to merchant, 1% to FeeRouter
   - Advances `nextChargeAt` by one cycle
   - Failed pulls emit `ChargeFailed`, increment `failedAttempts`, never revert

4. **Dunning:** At `maxFailed` failures → PAST_DUE. At `2 × maxFailed` → auto-paused inside `charge()`. Keeper retries at 1, 3, 7 days (configurable).

5. **Cancel:** Subscriber or merchant calls `cancelSubscription()`. Terminal; `charge()` reverts on cancelled subs.

## 2. Smart Contract Security Findings

### 2.1 Pull-Payment Model Analysis

**Can a merchant over-pull?**  
No. `charge()` reads `plan.price` from storage keyed by `sub.planId`, which the merchant cannot change after the subscriber joined. Plan prices are immutable.

**Can the keeper double-charge within a period?**  
No. `charge()` checks `block.timestamp >= sub.nextChargeAt` and advances `nextChargeAt` by exactly `plan.cycleSeconds` on success. A second call in the same period reverts `NotChargeable`.

**Can a cancelled subscription be charged?**  
No. Status check at `SubscriptionManager.sol:218-222` reverts on PAUSED or CANCELLED.

**Can a changed price be charged without consent?**  
No. Plan prices are immutable. Repricing requires a new plan; the subscriber must explicitly call `changePlan()`.

### 2.2 Findings

#### [H-1] Permissionless Failure Attack Bypasses Dunning Schedule

**Severity:** High  
**Location:** `src/SubscriptionManager.sol:214-290` (`charge()` and `_recordFailure()`)

The `charge()` function is permissionless: anyone can call it, not just the keeper. When a pull fails (subscriber has insufficient allowance), `_recordFailure()` increments `failedAttempts` but does NOT:
1. Advance `nextChargeAt` to enforce a retry interval
2. Record any `lastFailedAt` timestamp
3. Check any cooldown before accepting another failure

This means an attacker can call `charge()` in a loop—in a single block or even a single transaction—to instantly push a subscription from ACTIVE → PAST_DUE → PAUSED, completely bypassing the intended 1/3/7-day off-chain dunning schedule.

```solidity
function charge(uint256 subId) external nonReentrant {
    // ...
    if (!_collect(subId, sub, plan)) {
        _recordFailure(subId, sub, plan);  // No cooldown check!
        return;  // nextChargeAt NOT advanced on failure
    }
    sub.nextChargeAt = sub.nextChargeAt + uint64(plan.cycleSeconds);  // Only on success
}

function _recordFailure(...) internal {
    sub.failedAttempts += 1;  // Incremented every call
    if (sub.failedAttempts >= plan.maxFailed) sub.status = Status.PAST_DUE;
    if (sub.failedAttempts >= uint256(plan.maxFailed) * 2) {
        sub.status = Status.PAUSED;  // Can reach in one block!
    }
}
```

**Attack scenario:** A subscriber's allowance runs out. Before they can top up, a griefing bot (or competitor, or malicious merchant) calls `charge()` 4 times (with `maxFailed=2`) and the subscription is auto-paused. The subscriber never received the dunning emails they expected.

**Proof of concept:** See `test/PermissionlessFailure.t.sol`:
- `testPermissionlessFailureAttack()` demonstrates 4 sequential calls forcing PAUSED
- `testPermissionlessFailureOneTransaction()` shows the same via a helper contract in one tx
- `testFullyFundedSubscriberIsSafe()` confirms funded subscribers are protected (charge succeeds, further calls revert)

**63/64 gas rule assessment:** Could an attacker force a failure for a fully-funded subscriber by providing minimal gas, exploiting the EVM's 63/64 rule to make the inner `transferFrom` fail? The test `testGasLimitedCallCannotForceFailure()` shows that low-gas calls either succeed normally or revert the entire transaction—they do not record a failure. This is because Solidity's try/catch ensures sufficient gas is reserved, or the outer call reverts. **Conclusion: The 63/64 rule cannot be exploited to force failures for funded subscribers.**

**Recommendation (on-chain fix):** Store a `lastFailedAt` timestamp in the Subscription struct. In `_recordFailure()`, revert or return early if `block.timestamp < lastFailedAt + minRetryInterval`. The currently unused `graceSeconds` field in the Plan struct could serve this purpose—repurpose it as the minimum retry interval. This enforces the dunning schedule on-chain rather than relying on off-chain keeper behavior.

```solidity
function _recordFailure(uint256 subId, Subscription storage sub, Plan storage plan) internal {
    if (block.timestamp < sub.lastFailedAt + plan.graceSeconds) return; // Cooldown
    sub.lastFailedAt = uint64(block.timestamp);
    sub.failedAttempts += 1;
    // ... rest unchanged
}
```

#### [L-1] CEI Order Inverted in `_collect`

**Severity:** Low  
**Location:** `src/SubscriptionManager.sol:241-259`

State updates (`chargeCount`, `credit`) happen *after* external calls (`transferFrom`, `safeTransfer`). With standard USDC (no transfer hooks), this is safe. With any token that makes callbacks, a reentrancy from `pause/resume/cancel` (which are not guarded) could corrupt state.

However, USDC has no transfer hooks, and `charge()`, `subscribe()`, and `changePlan()` are already `nonReentrant`. The practical risk is negligible.

```solidity
// Current order (effects after interactions):
if (!_tryPull(sub.subscriber, due)) return false;
sub.credit = 0;  // effect after external call
fee = due / FEE_BPS;
usdc.safeTransfer(plan.merchant, due - fee);
usdc.safeTransfer(feeRouter, fee);
sub.chargeCount += 1;  // effect after external call
```

**Recommendation:** Reorder to checks-effects-interactions if supporting other tokens in the future, or add `nonReentrant` to `pauseSubscription`, `resumeSubscription`, `cancelSubscription`.

**Note:** The self-review (`SECURITY_REVIEW.md` §2) acknowledges this. Safe with USDC; flag for auditor.

#### [L-2] `setTreasury` Can Move Fees to an Uncontrolled Address

**Severity:** Low  
**Location:** `src/FeeRouter.sol:39-44`

The current treasury can set a new treasury to any non-zero address, including an EOA with lost keys. Fees would then be locked forever. However, only the treasury itself can call this function, and on mainnet the treasury is required to be a Safe multisig (enforced at deploy).

```solidity
function setTreasury(address _treasury) external {
    if (msg.sender != treasury) revert OnlyTreasury();
    if (_treasury == address(0)) revert ZeroAddress();
    // No check that _treasury is a contract or Safe
    treasury = _treasury;
}
```

**Recommendation:** Consider adding a timelock or requiring the new treasury to be a contract.

---

#### [L-3] Permit Nonce Front-Running

**Severity:** Low  
**Location:** `src/SubscriptionManager.sol:170-179`

Anyone who sees a Permit2 signature in the mempool can submit it to Permit2 directly, consuming the nonce. `subscribeWithPermit2` then reverts. The subscriber must retry with plain `subscribe()` (the allowance was still granted to Levy).

**Impact:** Griefing; no fund loss. Already documented in `SECURITY_REVIEW.md` §6.

---

#### [L-4] Plan Spam Can Cost Keeper Gas Indefinitely

**Severity:** Low  
**Location:** `src/SubscriptionManager.sol:123-146`

Anyone can create a 1-unit plan, subscribe to themselves, and the keeper pays gas to charge it daily. The `MIN_CYCLE = 1 day` bounds this to one charge/day, but there's no limit on the number of such subscriptions.

**Mitigation:** Monitor keeper gas spend; add a keeper-side policy to skip subscriptions whose fee doesn't cover gas (mentioned in `SECURITY_REVIEW.md` §3).

---

#### [L-5] `graceSeconds` Is Stored But Unused

**Severity:** Low  
**Location:** `src/SubscriptionManager.sol:44`

The `Plan` struct has `graceSeconds`, but nothing in the contracts uses it. The README says "informational; dunning schedule lives off-chain."

**Recommendation:** Remove from the struct to save storage gas, or repurpose it for the H-1 fix as a minimum retry interval.

---

#### [L-6] Resume/ChangePlan Forgive Overdue Cycles

**Severity:** Low (design choice)  
**Location:** `src/SubscriptionManager.sol:307-308`, `src/SubscriptionManager.sol:357`

`resumeSubscription` moves a passed `nextChargeAt` to the resume time. `changePlan` sets it to `now + newCycleSeconds`. Both forgive any overdue cycles rather than catching them up.

This is economically equivalent to cancel-and-resubscribe. Whether this is intended behavior should be confirmed with the product owner.

---

#### [L-7] No Event on Plan Creation Includes All Parameters

**Severity:** Low  
**Location:** `src/SubscriptionManager.sol:78`

`PlanCreated` emits `planId, merchant, price, cycleSeconds` but not `trialSeconds`, `graceSeconds`, or `maxFailed`. Off-chain indexers must call `plans(planId)` to get the full plan.

---

#### [INFO-1] Fee Rounding Favors Merchant

The fee is `amount / 100`, integer division rounding down. Up to 0.99 USDC units per charge go to the merchant instead of the protocol. Documented and intentional.

#### [INFO-2] No Owner, Pause, or Upgrade Powers (Positive)

**This is a security positive.** Neither contract has an owner, admin key, pause mechanism, or upgrade proxy. There is no rug vector: no address can freeze subscriber funds, drain the contract, or change the rules after deployment. Subscribers and merchants get predictable, immutable behavior.

The trade-off is that a bug requires redeployment and migration, but for a billing system handling other people's money, the absence of admin keys is the right choice.

#### [INFO-3] PUSH0 Compatibility

The contracts compile with `evmVersion: paris`, but Arc mainnet runs Osaka (PUSH0 works). The `paris` pin is harmless; could be removed.

#### [INFO-4] USDC Blocklist Behavior

If Circle blocklists a merchant's address or the FeeRouter, `safeTransfer` reverts and every charge for that merchant's plans fails. The subscriber is not charged; the keeper backs off. Only a new plan with a different merchant address fixes it.

#### [INFO-5] No Contract Existence Check on USDC Before Charge

**Location:** `src/SubscriptionManager.sol:267-276`

`_tryPull` calls `usdc.transferFrom`. If USDC were self-destructed (impossible in practice for Circle USDC), `try ... returns (bool ok)` would succeed with `ok = false`. The deploy script enforces USDC has code at deploy time.

**Practical risk:** Negligible for Circle USDC.

#### [INFO-6] `uint160` Cap for Permit2 Is Economically Irrelevant

**Location:** `src/SubscriptionManager.sol:270-276`

Permit2's `transferFrom` takes `uint160 amount`. The guard correctly returns `false` for amounts above `type(uint160).max`:

```solidity
if (amount > type(uint160).max) return false;
```

This means a subscription with `price > 1.46e48` USDC units (~$1.46e42) cannot be charged via Permit2. Economically irrelevant.

## 3. Off-Chain Security Findings

### 3.1 Keeper Key Handling

**How it works:** The keeper loads `LEVY_KEEPER_KEY` from environment variables, never from files in the repo. The key pays gas in USDC and can only call `charge()` (which is permissionless anyway).

**Blast radius:** A stolen keeper key cannot steal funds—`charge()` sends money to the merchant, not the caller. An attacker could:
1. Drain the keeper wallet's gas balance
2. Charge subscriptions early (not possible: contract enforces `nextChargeAt`)
3. DOS by submitting bad transactions

**Recommendation:** The key is low-risk. Fund minimally (the README says 0.12 USDC deployed the contracts). Consider a hardware wallet or KMS for mainnet.

---

#### [INFO-7] Keeper Coordination Is Off-Chain Concern

**Location:** `keeper/src/keeper.ts`, `keeper/README.md`

Two keepers running simultaneously would each record a failure for the same missed charge, exacerbating H-1. The README explicitly warns against running multiple instances.

**Note:** This is now secondary to H-1—the on-chain permissionless failure attack is the root cause. Even a single keeper cannot prevent a malicious actor from griefing subscriptions. Fix H-1 on-chain to address both concerns.

---

#### [L-8] No Rate Limiting on `POST /api/auth/challenge`

**Severity:** Low  
**Location:** `api/src/auth.ts:54`, `SECURITY_REVIEW.md` §10

Pending challenges are capped at 10,000, but there's no per-IP rate limit. An attacker could exhaust the cap and prevent legitimate sign-ins.

**Recommendation:** Add rate limiting at the reverse proxy (nginx) or in the app.

---

#### [L-9] Session Token in localStorage

**Severity:** Low  
**Location:** `api/public/auth.js`

Bearer tokens are stored in `localStorage`, making them accessible to XSS. No Content Security Policy is set.

**Recommendation:** 
- Add a strict CSP header
- Consider `httpOnly` cookies instead of localStorage tokens
- Or accept this risk for a dashboard that handles no funds

---

#### [L-10] `X-Levy-Event` Header Not Signed

**Severity:** Low  
**Location:** `keeper/src/webhooks.ts:420-432`

The signature covers `timestamp.deliveryId.body`, but not the `X-Levy-Event` header. A MITM could change the event type header without invalidating the signature.

**Recommendation:** Include the event type in the signed content, or document that merchants should use the `type` field inside the body.

---

#### [INFO-8] Webhook SSRF Protection Is Solid

The URL validation at `keeper/src/webhook-url.ts` is comprehensive:
- IPv4: blocks loopback, private, link-local, carrier-grade NAT, multicast, documentation, reserved
- IPv6: allowlist for global unicast only
- Checked at registration AND at connect time (DNS rebinding defense)
- Redirects never followed
- Port 443 only
- No credentials in URL

This is better than many production systems.

#### [INFO-9] ERC-1271 Not Supported

Contract wallets (Gnosis Safe, etc.) cannot sign in. EOA signatures only. Documented in `SECURITY_REVIEW.md` §10.

## 4. Correctness and Reliability

### 4.1 Keeper Failure Modes

| Failure Mode | Behavior | Recovery |
|--------------|----------|----------|
| Missed runs | Charges accumulate; keeper catches up on restart | Automatic |
| Reorgs | Arc has single-block deterministic finality; N/A | N/A |
| Gas spikes | Keeper pays more; charges might fail if wallet runs dry | Monitor balance; top up |
| Partial batches | Each charge is independent; failures don't block others | Automatic |
| Restart | In-memory backoff state is lost; one extra retry per stuck sub | Acceptable |

### 4.2 API/DB Drift from Chain

The keeper's indexer reads chain events as the source of truth and upserts into SQLite. Charge truth comes from `Charged`/`ChargeFailed` events, not transfer sums. This is correct.

The API reads from the same SQLite database. As long as the keeper is running and synced, the API reflects chain state within one sync cycle (30 seconds).

**Gap:** If the keeper crashes, the API shows stale data. Consider adding a "last synced at" indicator to the dashboard.

### 5.2 Invariant Fuzzing

The CI profile runs invariants at 1000 runs × depth 40. Invariants tested:
- `invariant_conservation`: Every minted USDC unit is accounted for
- `invariant_failedAttemptsBounded`: `failedAttempts <= 2 × maxFailed`
- `invariant_cancelIsTerminal`: `chargeCount` never moves after cancel
- `invariant_nextChargeMonotonic`: `nextChargeAt >= start`
- `invariant_creditBacked`: Credit never exceeds USDC paid
- `invariant_creditBounded`: Credit never exceeds largest plan price
- `invariant_managerHoldsNothing`: Manager balance is always zero

The fuzzer found real bugs (documented in `FEE_MATH_AUDIT.md` §5): the `uint8` overflow in `maxFailed * 2` and the resume keeping failure count.

- No test for USDC `transferFrom` returning `false` without reverting (non-standard behavior)
- No test for chain reorgs (irrelevant for Arc's deterministic finality)
- No test for keeper running out of gas mid-batch
- No fuzz testing of the TypeScript keeper logic
- Permit2 tested against a mock, not the real Arc Permit2

## 8. Product Notes

### 8.1 Positioning

Levy targets a real gap: no subscription billing exists on Arc. The "Stripe Billing for crypto" framing is accurate. The 1% fee is competitive with Request Finance ($600-$9000/mo) for merchants with significant volume.

### 8.2 Merchant Adoption Barriers

1. **No plan creation UI:** Merchants must call `createPlan` from their wallet or use cast. This is fine for early adopters but blocks non-technical merchants.

2. **Allowance UX:** Subscribers must understand and approve ERC-20 allowances. The checkout page helps, but this is still crypto-native friction.

3. **No fiat off-ramps:** USDC stays in USDC. Merchants who need fiat must bridge and off-ramp elsewhere.

4. **No refunds:** Documented as merchant policy, handled off-chain. Some merchants will want on-chain refund capability.

### 8.3 What Would Make a Merchant Adopt

- Proven reliability: Complete the soak, get an audit, run for months without incident
- Integration ease: Add webhooks for their existing billing system; the 10 event types are well-designed
- Volume: Enough users on Arc willing to pay in USDC
- Regulatory clarity: Stablecoin billing has tax and accounting implications that vary by jurisdiction
